# Authentication System

A complete, production-ready authentication system built on NextAuth
(Auth.js) v5, Prisma, and PostgreSQL. This document covers local setup and
the architecture decisions behind it — see inline comments in the files
themselves for the reasoning behind any specific line.

## Features

- Email/password registration with required email verification
- Login (credentials, Google OAuth, GitHub OAuth, magic links)
- Forgot password / reset password (one-time, hashed, expiring tokens)
- Role-based access control — `ADMIN` > `MANAGER` > `EDITOR` > `CUSTOMER`
- Protected routes via middleware + a second, authoritative server-side check
- JWT sessions in secure, httpOnly cookies, with a revocation mechanism
  (see "Session model" below)
- Redis-backed rate limiting (in-memory fallback for local dev) on every
  auth endpoint that can be abused (login, register, forgot-password,
  resend-verification, magic link)
- Zod validation shared between client UX and server-side enforcement
- Generic, anti-enumeration responses on login and forgot-password

## Local setup

1. **Database.** Point `DATABASE_URL` in `.env.local` at a PostgreSQL
   instance, then run:
   ```bash
   npx prisma migrate dev
   ```
   This creates every table in `prisma/schema.prisma` (`User`, `Account`,
   `Session`, `VerificationToken`, `EmailVerificationToken`,
   `PasswordResetToken`) and generates the Prisma Client to
   `generated/prisma` (gitignored — regenerated by `postinstall`/`migrate`,
   never hand-edited).

2. **Auth secret.** Generate one and set it as `NEXTAUTH_SECRET`:
   ```bash
   npx auth secret   # or: openssl rand -base64 32
   ```

3. **Email.** Without `RESEND_API_KEY` set, every verification/reset/
   magic-link email is logged to the server console instead of sent —
   local development and this repo's own testing never required a real
   Resend account. Set `RESEND_API_KEY` and `RESEND_FROM_EMAIL` to send
   real email.

4. **OAuth (optional).** Set `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`
   and/or `GITHUB_CLIENT_ID`/`GITHUB_CLIENT_SECRET` to enable those
   providers — each is only registered in `src/auth.ts` when its pair of
   env vars is present, so the app runs fine with neither configured
   (those buttons just aren't offered).

5. **Rate limiting.** Without `REDIS_URL`, `lib/auth/rate-limit.ts` falls
   back to an in-process counter — correct for local dev, **not**
   appropriate for a multi-instance production deployment (each instance
   would have its own counter). Set `REDIS_URL` in any real deployment.

6. **Promoting a user's role.** There's no admin UI for this yet (out of
   scope for this pass) — set it directly:
   ```sql
   UPDATE "User" SET role = 'ADMIN' WHERE email = 'you@example.com';
   ```

## Architecture

### Why JWT sessions (not database sessions)

The Prisma adapter is still wired up — it owns `User`/`Account` (OAuth
linking) and the `VerificationToken` table the magic-link provider needs —
but the actual session strategy is `"jwt"`, not the adapter's
database-session tables. A stateless JWT can't be revoked by deleting a
row, so revocation is handled by `User.tokenVersion`: every token embeds
the version that was current when it was issued, and `auth.ts`'s `jwt`
callback re-checks it against the database (throttled to once a minute,
not on every request) — a mismatch marks the session `revoked`, which
`lib/auth/guards.ts` and `middleware.ts` both treat as "no session."
Password reset bumps `tokenVersion`, so resetting a password signs out
every other device/session too, not just the one performing the reset.

### Edge/Node split (`auth.config.ts` vs `auth.ts`)

`middleware.ts` runs on the Edge runtime by default, which can't load
Prisma, bcrypt, or ioredis (all Node-only). `auth.config.ts` holds the
subset of NextAuth config that's Edge-safe (pages, the pure parts of the
`jwt`/`session` callbacks) and is all `middleware.ts` imports. `auth.ts`
spreads that config and adds the Prisma adapter, real providers, and the
database-backed parts of the callbacks — used everywhere else (the
`/api/auth/[...nextauth]` route, Server Actions, Server Components).

### Defense in depth (RBAC)

Every protected route is checked twice, deliberately:
1. **`middleware.ts`** — fast, Edge-safe, decodes the JWT and redirects
   before the route even renders. This is the UX layer, not the security
   boundary — it can be bypassed by invoking a Server Action directly.
2. **`lib/auth/guards.ts`'s `requireAuth`/`requireRole`** — called inside
   every protected Server Component/Server Action, re-verifying against
   the live database. This is the actual authority; see `src/app/(app)/`
   for both route-level (`requireRole("MANAGER")` on `/admin`) and
   section-level (`hasMinimumRole(role, "ADMIN")` gating one card within
   that same page) examples of the same check composing at different
   granularities.

### Anti-enumeration

Login and forgot-password never reveal whether a specific email has an
account: forgot-password always returns the same message regardless, and
login's `Credentials.authorize()` collapses "unknown email," "wrong
password," and "account locked" into the same generic `null` return
(NextAuth's own docs recommend exactly this). The two exceptions —
rate-limit errors and "please verify your email" — are deliberate,
documented trade-offs explained in `src/auth.ts`, not oversights.

### Token storage

Every emailed token (verification, password reset) is a 256-bit random
value; only its SHA-256 hash is ever written to the database
(`lib/auth/tokens.ts`). A database export is useless for account
takeover on its own — an attacker would still need the raw token, which
only ever existed in an email already delivered to the real address.
