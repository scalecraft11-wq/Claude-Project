# Backup Strategy

What actually needs backing up, and what doesn't, for this application.

## What holds real, irreplaceable state

| System | Contains | Backup approach |
|---|---|---|
| **PostgreSQL** | Everything: users, orders, products, content, sessions (via the Prisma adapter), activity logs — the entire application's state | See below — this is the one that matters |
| **Cloudinary** | Uploaded product/blog images | Already durable/replicated by Cloudinary itself; no separate backup needed for the files themselves (see note below) |
| **Redis** | Cache entries and rate-limit counters only | **No backup needed** — see below |

## PostgreSQL

This is the only system where data loss would be unrecoverable without a
backup, so it's the one to actually invest in.

### If using a managed provider (recommended)

Neon, Supabase, and RDS all provide automated backups out of the box:

- **Neon**: point-in-time restore built in (retention depends on plan) —
  no configuration needed beyond picking a retention window.
- **Supabase**: daily backups on paid plans, point-in-time recovery on
  higher tiers — check your plan's retention window.
- **RDS**: enable automated backups (on by default on creation, but
  verify) with a retention period; consider also enabling a final
  snapshot on any planned deletion.

**Action item**: whichever provider you use, confirm the retention window
actually matches how far back you'd need to recover from (7 days is often
too short for "we didn't notice this data problem for two weeks").

### If self-hosting Postgres (Docker/VM)

Automate `pg_dump` on a schedule — this repo doesn't include a backup
cron, since the right schedule/retention/storage target depends entirely
on your infrastructure. A minimal cron-based approach:

```bash
# Nightly full dump, compressed, kept 14 days — adjust retention to your
# recovery-point requirements.
0 2 * * * pg_dump "$DATABASE_URL" | gzip > /backups/lumora-$(date +\%Y\%m\%d).sql.gz
find /backups -name "lumora-*.sql.gz" -mtime +14 -delete
```

Store dumps somewhere other than the same disk as the database (S3,
another host, a managed backup service) — a backup that dies with the
same machine it was protecting against isn't a backup.

**Test the restore, not just the dump.** A backup you've never restored
from is a hypothesis, not a backup. See
[RECOVERY.md](./RECOVERY.md#restoring-postgresql-from-a-backup) and
actually run it against a scratch database periodically.

## Redis — deliberately not backed up

Everything in Redis (`src/lib/redis.ts`, `src/lib/cache.ts`) is either a
cache-aside entry (safely rebuildable from Postgres on a cache miss) or a
rate-limit counter (loses at most a short window of rate-limit state,
never anything users would notice as data loss). Losing all of Redis is
equivalent to a cold cache — a brief performance dip, not an incident.
Don't spend backup budget here.

## Cloudinary — media assets

Cloudinary itself replicates stored assets; you're not responsible for
backing up the binary files. What you *are* responsible for is the
association between a `MediaAsset.publicId` (in Postgres) and the actual
Cloudinary asset — which is exactly why the Postgres backup above is the
real dependency. If Postgres is restored to a point before an upload, the
Cloudinary asset itself still exists (Cloudinary doesn't delete on its
own schedule) but the database row pointing to it won't — a orphaned
asset, not a data-loss problem.

## What's NOT backed up, and why that's fine

- **`.next` build output** — regenerated by the next deploy; never
  hand-edited, never a source of truth.
- **Environment variables** — these live in Vercel's dashboard / your
  `.env` file, not in application data. Keep a secure copy (a password
  manager, not a plaintext file) of anything not trivially regeneratable
  (API keys from third parties) as a matter of general secret hygiene,
  separate from this backup strategy.
- **Sentry issue history** — Sentry retains its own data per its plan;
  not this app's responsibility to back up.

## Backup checklist (do this now, not during an incident)

- [ ] Confirm your Postgres provider's automated backup is actually
      enabled and its retention window is documented somewhere your team
      can find it.
- [ ] If self-hosting, set up the `pg_dump` cron above (or equivalent)
      and confirm dumps are landing somewhere durable.
- [ ] Actually perform one test restore (see RECOVERY.md) and time how
      long it takes — that number is what you tell people during a real
      incident.
- [ ] Store `NEXTAUTH_SECRET`, Stripe keys, and other credentials in a
      password manager or secrets vault, not only in the deployment
      platform's env var UI.
